## Research Findings (Research Agent)
All verified empirically against `Godot_v4.7.1-stable_win64_console.exe` in throwaway probe copies, deleted after; real repo untouched.

1. **`StanceData` extension is safe:** `@export` syntax confirmed for all 5 properties; extended a copy and re-ran the full Step 4 smoke test suite clean. `.tres` format verified: `type="Resource"` + `script_class="StanceData"` (NOT `type="StanceData"`), hand-authored files load fine. **Gotcha:** `ResourceSaver` silently omits any property equal to the script's default — give script defaults deliberately invalid/neutral values (e.g. `0.0`) so every stance `.tres` carries explicit values, or hand-author `.tres` files directly (Step 3's InputMap precedent) rather than trusting `ResourceSaver`. **Gotcha 2:** typed signal params are not runtime-enforced — `stance_swapped` will accept a plain `Resource` with no error; any consumer needs its own `is StanceData` guard.

2. **AnimationPlayer method-only tracks work headlessly** (bare `TYPE_METHOD` track, zero animated properties) — verified both `callback_mode_method` DEFERRED and IMMEDIATE fire correctly and on time. **Real bug found:** an active window shorter than ~1 full physics tick registers **zero hits** — enable/disable keys 0.30-0.72 ticks apart produced 0 hits every time; only a >=1-tick gap reliably hit. Also: `area_entered` fires **one physics tick after** `monitoring=true`, not the same tick — CLAUDE.md 5.2's "frame-accurate" is really frame+1. Recommend enforcing a hard floor of >=3 physics ticks (0.05s) on any active window.

3. **`area_entered` semantics, verified matrix:**
   - Detection requires detector `monitoring=true` + target `monitorable=true`; target's own `monitoring` is irrelevant, so hurtboxes should be `monitoring=false` (halves collision pairs — helps Step 14's budget) and hitboxes `monitorable=false` (makes hitbox-vs-hitbox structurally impossible).
   - `area_entered` (not `body_entered` — that's `PhysicsBody3D`-only) fires **once on entry**, not per-frame while overlapping (confirmed: 30 continuous overlapping frames, 0 extra events) — no per-frame multi-hit risk. **But** every `monitoring` false->true re-fires `area_entered` even with zero movement, so two enable windows in one swing = 2 hits unless a per-window `_hit_this_window` set is cleared in `enable_hitbox()`.
   - **Self-hit bug found:** with hitbox/hurtbox sharing one layer, an attacker's own hitbox hits its own hurtbox (reproduced). **Fix verified:** split layers — 6=PLAYER_HURTBOX, 7=ENEMY_HURTBOX, 8=HITBOX; each side's hitbox masks only the opposing hurtbox layer. Eliminates self-hit and hitbox-vs-hitbox at zero runtime cost.
   - i-frames confirmed: disabling the hurtbox's `CollisionShape3D` (per Step 14's "disable the shape, not the Area3D" note) blocks the hit entirely and re-enabling restores it — Step 4's `is_invulnerable` can drive this directly.

4. **Real charter gap found:** CLAUDE.md 5.2 references a "blocking" state ("if target is blocking, reduce incoming damage...") but **Step 3's InputMap has no `block` action at all** — only `parry`, `light_attack`, `heavy_attack`, `dodge`, `stance_next/prev`, `interact`. There is currently no player input that could ever set `is_blocking=true`. This needs a Director ruling: implement `is_blocking` as pure exposed state (settable via a method, for future wiring) without binding it to any input this step, vs. adding a new InputMap action retroactively (bigger scope creep into Step 3's territory), vs. treating some stances' block-check as dead code until a later step defines how blocking is triggered.

5. **Scoping (Research's read, not a ruling):**
   - **Stats:** a `Combatant` base script (`scripts/combat/combatant.gd`, extends `Node3D`) owning `health/max_health/posture/max_posture/armor` + `take_damage(amount, posture_damage, attacker)`, each `# TODO(Step 11/14): migrate to PlayerData`, matching Step 4's stamina-stub precedent. Must emit the charter's real signals (`entity_damaged`, `posture_broken`, `parry_executed` — already declared on `EventBus` since Step 2, not new) but must NOT emit `player_health_changed`/`player_posture_changed` (those carry a `max` value Step 11's HUD would bind to as fact).
   - **Test actors:** two instances of one generic `scenes/combat/combatant.tscn` (`Combatant` + `Hurtbox` Area3D + `Weapon/Hitbox` Area3D + an `AnimationPlayer` with the method track), not reusing `player.tscn` directly — lets Step 7's enemy extend `combatant.gd` later instead of deleting Step 5 scaffolding. `player.gd` gains a `Hurtbox` child wired to `is_invulnerable`.
   - **Parry:** minimal `is_parrying` flag on `Combatant`, set by consuming `InputBuffer.consume_action(&"parry")` for `active_stance.parry_window_duration`'s tick-equivalent (tick counter, per Step 4's precedent, not a float timer). Deliberately out of scope: parry counter-animation, stagger animation, hit-stop (Step 6) — the `-40%` posture penalty is just arithmetic, include it.

## Approach & Tradeoffs (Director sign-off)
- **`StanceData`:** extend the existing stub with the 5 real properties (all defaults set to deliberately-invalid neutral values, e.g. `0.0`/`""`, per Research's `ResourceSaver`-omission gotcha). Author the 4 `.tres` stances **by hand** (Step 3's InputMap precedent), not via a `ResourceSaver` script, to sidestep that gotcha entirely — every stance's values will be explicit in the file regardless of script defaults.
- **Collision layers (new, added to `project.godot`'s `[layer_names]` for clarity):** layer 6 = `player_hurtbox`, layer 7 = `enemy_hurtbox`, layer 8 = `hitbox`. Hurtboxes: `monitoring=false`, `monitorable=true`, on their own side's layer. Hitboxes: `monitorable=false`, `monitoring` toggled by `enable_hitbox()`/`disable_hitbox()`, `collision_mask` set to the *opposing* hurtbox layer only (an `owner_actor` reference on `Combatant` is also required, checked in `area_entered` as a second guard — belt-and-suspenders with layer separation, per Research's recommendation for Step 8's stance-mirroring/friendly-fire needs later).
- **Hitbox activation is real `AnimationPlayer` method-call tracks** (`enable_hitbox()`/`disable_hitbox()`), not a driving timer/script stand-in — Research proved this works headlessly with zero animated properties, so there's no need to fake it. **Minimum active window: >=3 physics ticks (0.05s), enforced as a documented constraint** (comment on `Combatant.enable_hitbox()` and asserted in the Step 5 test's own authored animation) rather than a runtime safeguard — Research's sub-tick-window bug is an authoring mistake to avoid, not a case to silently correct at runtime (silently extending an authored window would itself be surprising behavior). Flag for Step 13's animators.
- **Per-window hit dedup:** `Combatant` (or the hitbox script) keeps `_hit_this_window: Array[Node]`, cleared in `enable_hitbox()`, checked/appended in `_on_hitbox_area_entered()` before resolving a hit — prevents the verified double-hit-per-swing bug from two enable windows or re-entry.
- **Block-state charter gap ruling:** CLAUDE.md 5.2's block-check is real logic (80% mitigation + full posture damage) but **no InputMap action exists for "block."** Implementing `is_blocking: bool` as pure exposed state with a public `set_blocking(value: bool)` method — NOT wired to any input this step. This keeps the block-check branch testable (QA can set the flag directly) and the resolution logic real, without inventing a new InputMap action (out of Step 5's scope, and Step 3's action list is meant to be the complete input surface) or silently dropping the block-check entirely. Logged here as a real, standing charter gap: **something in a later step (or a charter amendment) needs to define how a player actually enters a blocking state** — possibly stance-specific (Stone's "high poise" text hints at a blocking-adjacent identity), but that's a design call outside Step 5's scope.
- **Parry:** `is_parrying: bool` on `Combatant`, set when consuming `InputBuffer.consume_action(&"parry")`, held for `roundi(active_stance.parry_window_duration * 60)` physics ticks (tick counter, per Step 4's precedent — e.g. Stone's 0.12s window = 7 ticks).
- **Damage/posture formula:** using Section 2's canonical `ArmorMitigation = Armor / (Armor + 100)` (5.2's restated formula is the same shape, just without a separate weapon term — no weapon system exists yet, Step 10/13 territory, so `take_damage(base_damage, posture_damage, attacker)` takes one pre-combined damage number). On a **hit**: `health -= base_damage * stance.base_damage_multiplier * (1 - mitigation)`; `posture -= posture_damage * stance.posture_damage_multiplier * (1 - mitigation)`; emit `EventBus.entity_damaged(self, health_delta, false)`, and `EventBus.posture_broken(self)` if posture crosses 0. On **parry** (checked first): attacker's posture -= 40% of attacker's `max_posture`, emit `EventBus.parry_executed(attacker, self)`, no health/posture change to the defender. On **block** (checked second, only if not parried): incoming health damage *0.2 (80% mitigation), but full (unmitigated-by-block) posture damage still applies, per 5.2's literal wording. **Judgment call, logged:** the exact posture-damage formula for hit/block isn't fully specified in CLAUDE.md beyond "deduct posture" — using the same stance-multiplier/armor-mitigation shape as health for hits (not for block, where 5.2 explicitly says "full posture damage" bypassing mitigation) is the most internally consistent reading, not a verbatim charter quote.
- **Stats:** `Combatant` (`extends Node3D`) with `health/max_health/posture/max_posture/armor`, each initialized to real (non-fake) numbers for test purposes, per Research's Step-4-precedent framing — no `EventBus.player_*_changed` emission (Step 11 territory).
- **Scene layout:** `scenes/combat/combatant.tscn` (generic, reusable by Step 7's future enemy) + `scripts/combat/combatant.gd`. `player.gd`/`player.tscn` gains a `Hurtbox` child (layer `player_hurtbox`) wired so `is_invulnerable` disables its `CollisionShape3D`, per Step 4's accessor and Research's verified i-frame mechanism — but the player does NOT become a full `Combatant` this step (that would mean retrofitting Step 4's player controller into a new base class, wider-reaching than Step 5's scope); it just gains the same hurtbox+stat pattern via composition. Test harness at `scripts/tests/combat_test.gd/.tscn` (Step 3/4 convention) using two bare `combatant.tscn` instances (attacker/defender), not `player.tscn`.
- **Testing:** headless scene-mode test per established pattern, asserting: (1) a normal hit reduces health/posture by the correct stance/armor-mitigated amounts and emits `entity_damaged`; (2) parry (via `is_parrying=true` at the moment of the incoming hit) resolves as a parry, not a hit — attacker posture drops, `parry_executed` emitted, defender health/posture unchanged; (3) block (`is_blocking=true`) resolves as reduced health damage + full posture damage; (4) the sub-tick-window authoring constraint is respected in the test's own animation (>=3 ticks); (5) the self-hit/hitbox-vs-hitbox layer fix — an attacker's hitbox does NOT register against its own hurtbox even if geometrically overlapping; (6) double-enable-window dedup — re-entering the hitbox's active window within one swing doesn't double-hit.

**Real bug found and fixed during test-writing (logged here since it affects anyone driving `enable_hitbox()`/`disable_hitbox()` manually in a script, e.g. future test code or a non-`AnimationPlayer` caller):** toggling a hitbox `monitoring` `true -> false -> true` with **no physics tick processed while it was `false`** (i.e. `disable_hitbox()` immediately followed by `enable_hitbox()` in the same script frame, no intervening `await get_tree().physics_frame`) does **not** produce a fresh `area_entered` for an already-overlapping pair — the physics engine never observes the `false` state long enough to register the "exit," so the following `true` isn't seen as a new "entry" either. This is different from Research's verified "every monitoring `false->true` refires `area_entered`" finding, which was tested with at least one physics tick elapsing at `monitoring=false` in between. Not a `Combatant` code bug — `combat_test.gd`'s `_trigger_hit_direct()` helper now `await`s one extra `get_tree().physics_frame` after `disable_hitbox()` to give the engine that tick. A real `AnimationPlayer`-driven attack (the actual Step 5 activation mechanism) is very unlikely to hit this edge case since successive swings are normally separated by many ticks of recovery/wind-up animation, but it's worth a note for Step 6/7/13 if any future code ever re-enables a hitbox on the very next line after disabling it.

**Deviations from the brief:** none substantive. `combat_test.gd`'s test 4 (animation-driven hit) required setting `AnimationPlayer.callback_mode_process = 0` (`PROCESS_PHYSICS`) on `combatant.tscn`'s `AnimationPlayer` — not explicitly specified in the brief, but necessary for the method-call track to actually advance in step with the test's `await get_tree().physics_frame`-driven loop (the `AnimationPlayer` default, `PROCESS_IDLE`, ticks on rendered frames instead); this also matches how the animation will actually run in real gameplay (physics-driven combat state).
